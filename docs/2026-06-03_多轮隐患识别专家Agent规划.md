# 多轮隐患识别专家 Agent 规划

日期：2026-06-03

## 1. 项目定位

本项目目标是构建一个基于微调视觉语言模型 API 的多轮对话式施工安全隐患识别专家 Agent。

Agent 不是单次图片识别接口，而是一个具备多轮对话、工具调用、视觉证据融合、规则解释、记忆管理和报告生成能力的专家系统。

核心定位：

```text
用户上传图片或指定历史图片
-> Agent 理解用户意图
-> Agent 调用微调 VLM API、YOLO 检测、规则检索等工具
-> Agent 融合视觉证据和规则依据
-> Agent 支持多轮追问、解释和报告生成
```

第一版采用“按需调用 VLM”的方案。VLM 不在后台持续进行实时视频逐帧分析，而是在用户请求、指定图片、指定区域或需要复核时由 Agent 调用。

## 2. 核心目标

第一阶段直接按高级版架构规划，但控制功能边界。

需要实现：

- 图片上传与历史图片选择。
- 多轮对话式隐患识别。
- 调用微调 VLM API 识别四口五临边隐患。
- 调用 YOLO 检测安全帽和人员。
- 调用本地规则库进行四口五临边规则检索。
- 融合 VLM、YOLO 和规则结果。
- 支持用户追问隐患依据、整改建议、不确定项。
- 生成结构化 JSON、带框图片和检查报告。
- 保存会话、图片、工具调用和分析结果。
- 支持人工复核和结果修正的扩展。

暂不实现：

- VLM 后台实时视频巡检。
- 多摄像头实时接入。
- 长视频连续轨迹分析。
- 复杂权限系统。
- 线上生产级部署。

## 3. 推荐技术栈

高级版推荐技术栈：

```text
后端：FastAPI
Agent 编排：LangGraph 或自定义状态机，优先预留 LangGraph
对话大脑：通用 LLM API
微调模型：外部 VLM API
目标检测：Ultralytics YOLO
图像处理：OpenCV + Pillow
数据库：PostgreSQL，开发期可先用 SQLite
缓存/任务队列：Redis
后台任务：Celery 或 RQ
文件存储：本地 uploads/outputs，后续可替换为 MinIO
前端：React / Next.js
报告输出：Markdown / HTML / PDF
```

## 4. 总体架构

```text
Frontend Chat UI
  ↓
FastAPI Backend
  ↓
SafetyExpertAgent
  ├── Intent Router
  ├── Memory Manager
  ├── Tool Planner
  ├── VLM Hazard Tool
  ├── YOLO Helmet Tool
  ├── Rule Retrieval Tool
  ├── Evidence Fusion Tool
  ├── Report Generator
  └── Human Review Tool
  ↓
PostgreSQL / SQLite + Redis + File Storage
```

模块职责：

- `Intent Router`：识别用户当前意图，例如图片分析、安全帽检测、隐患解释、报告生成。
- `Memory Manager`：读取和写入会话上下文、图片历史、分析结果和工具调用记录。
- `Tool Planner`：决定本轮需要调用哪些工具。
- `VLM Hazard Tool`：调用微调 VLM API 进行四口五临边隐患识别。
- `YOLO Helmet Tool`：检测人员、安全帽和未佩戴安全帽人员。
- `Rule Retrieval Tool`：基于 object_id 检索四口五临边规则块。
- `Evidence Fusion Tool`：融合 VLM、YOLO、规则和历史上下文。
- `Report Generator`：生成隐患检查报告。
- `Human Review Tool`：预留人工复核、修正和确认能力。

## 5. VLM 模块需求

微调 VLM API 作为视觉隐患专家工具，不负责 Agent 多轮对话编排。

需要支持的输入场景：

- 分析整张图片。
- 分析用户指定 bbox 或裁剪区域。
- 重新分析历史图片。
- 结合候选规则块判断隐患。
- 输出结构化 JSON。

建议 VLM API 输入包含：

```json
{
  "image_path": "uploads/example.jpg",
  "question": "识别图中的四口五临边安全隐患。",
  "candidate_rules": [],
  "target_bbox": null,
  "context": {
    "scene": "four_openings_edges"
  }
}
```

建议 VLM API 输出包含：

```json
{
  "objects": [
    {
      "object_id": "floor_edge_protection",
      "object_name": "楼层临边防护",
      "bbox": [120, 80, 780, 620],
      "status": "confirmed_hazard",
      "hazard_type_id": "missing_protection",
      "hazard_type": "防护缺失",
      "visual_evidence": "图中楼层临边未见连续防护栏杆。",
      "missing_evidence": null,
      "evidence_sufficiency": "sufficient",
      "uncertainty_reason": null,
      "rule": "楼层临边应设置防护栏杆或其他防坠落措施。",
      "confidence": 0.82
    }
  ],
  "summary": "发现 1 处楼层临边防护缺失隐患。"
}
```

## 6. YOLO 模块需求

YOLO 模块负责轻量目标检测，不承担四口五临边规则判断。

第一阶段检测类别：

```text
person
helmet
no_helmet
```

输出字段建议：

```json
{
  "detections": [
    {
      "label": "no_helmet",
      "bbox": [300, 120, 420, 500],
      "confidence": 0.91
    }
  ],
  "summary": {
    "person_count": 3,
    "helmet_count": 2,
    "no_helmet_count": 1
  }
}
```

后续可扩展：

- 人员跟踪。
- 危险区域进入判断。
- 靠近临边或洞口判断。
- 视频关键帧分析。

## 7. 多轮对话需求

Agent 必须支持基于历史上下文继续追问。

典型对话：

```text
用户：分析这张图有没有隐患。
Agent：发现 1 处楼层临边防护缺失，并检测到 1 名人员未佩戴安全帽。

用户：隐患依据是什么？
Agent：依据上一张图片中楼层临边区域的可见证据和规则 XXX。

用户：怎么整改？
Agent：建议设置连续防护栏杆，确认栏杆固定可靠，并对未戴安全帽人员进行纠正。

用户：生成一份报告。
Agent：生成包含图片、bbox、隐患清单、规则依据和整改建议的检查报告。
```

Agent 需要记住：

- 当前会话 ID。
- 用户上传的图片。
- 每张图片的 VLM 分析结果。
- 每张图片的 YOLO 检测结果。
- 每个隐患对象的 bbox、状态、规则和证据。
- 用户追问所指向的图片、对象或隐患。
- 已生成的报告。

## 8. 数据库规划

核心数据实体：

```text
conversations        会话
messages             用户和 Agent 消息
uploaded_files       上传图片或视频
tool_calls           工具调用日志
vlm_results          VLM 推理结果
yolo_results         YOLO 检测结果
fused_results        融合后的隐患结果
reports              检查报告
human_reviews        人工复核和修正记录
```

第一阶段可以使用 SQLite 快速开发，但表结构按 PostgreSQL 迁移设计。

Redis 用途：

- 后台任务队列。
- 长任务状态缓存。
- 工具调用临时结果缓存。
- 流式响应状态。
- 后续多实例共享状态。

## 9. Agent 工具规划

建议拆成原子工具，而不是一个大工具。

工具清单：

```text
upload_image_tool
query_memory_tool
rule_retrieval_tool
vlm_hazard_analysis_tool
yolo_helmet_detection_tool
draw_bbox_tool
evidence_fusion_tool
generate_report_tool
revise_result_tool
complete_task_tool
```

工具设计原则：

- 工具只做单一能力。
- Agent 决定调用顺序。
- 所有工具调用需要记录输入、输出和耗时。
- 高成本工具调用前应能复用历史结果。
- 结果必须结构化，方便追问和报告生成。

## 10. 核心流程

### 10.1 图片隐患识别流程

```text
用户上传图片并提问
-> 保存图片
-> 创建或读取会话
-> Agent 判断需要隐患识别
-> 调用规则检索
-> 调用微调 VLM API
-> 调用 YOLO 安全帽/人员检测
-> 融合结果
-> 生成带框图
-> 保存分析结果
-> 返回多轮回答
```

### 10.2 用户追问流程

```text
用户追问依据、整改建议或某个隐患
-> Agent 从会话记忆中定位图片和对象
-> 查询历史 VLM/YOLO/fused result
-> 必要时重新调用工具
-> 返回解释或建议
```

### 10.3 报告生成流程

```text
用户要求生成报告
-> Agent 读取当前会话分析结果
-> 汇总隐患清单、安全帽检测、不确定项、规则依据
-> 生成 Markdown/HTML 报告
-> 可选生成 PDF
-> 保存报告记录
-> 返回报告链接或内容
```

## 12. 验收标准

第一版高级 Agent 完成后，应满足：

- 用户可以上传施工现场图片。
- Agent 可以识别四口五临边隐患。
- Agent 可以识别人员和安全帽佩戴情况。
- Agent 可以输出 bbox、视觉证据、规则依据和整改建议。
- Agent 可以对上一轮结果进行追问解释。
- Agent 可以处理 `confirmed_hazard`、`safe`、`uncertain`。
- Agent 可以生成结构化 JSON 和检查报告。
- Agent 可以保存会话、图片、工具调用和分析结果。
- Agent 可以复用历史结果，避免重复调用高成本工具。
- Agent 的每次判断都有可追溯工具调用记录。

## 13. 风险和注意事项

- VLM API 必须稳定输出结构化 JSON，否则 Agent 难以融合证据。
- YOLO 安全帽检测 API 需要返回稳定的结构化结果，否则安全帽检测效果不可控。
- 规则检索第一版不要过度复杂，本地 JSON top-k 足够。
- Agent 对话大脑不要和微调 VLM 混为一体，二者职责不同。
- `uncertain` 必须保留，不能让 Agent 强行判断。
- 后台实时视频巡检不属于第一版核心范围。
- Redis 可以作为高级架构的一部分，但不要让它替代长期数据库。
