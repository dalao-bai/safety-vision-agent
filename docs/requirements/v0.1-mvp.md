# v0.1 MVP Requirements

Date: 2026-06-05

## Product Direction

Build a construction-site safety hazard identification Agent.

The project is being rebuilt from a clean slate. v0.1 should prove the smallest useful end-to-end loop instead of attempting the final product in one step.

## v0.1 Goal

Allow a local single user to upload one construction-site image, receive structured hazard analysis from a real VLM, and continue asking follow-up questions about the same image and analysis.

The first version must feel like an Agent because it uses model-driven tool calling, but its tool surface must remain small.

## Core User Flow

1. User opens a minimal web UI.
2. User uploads one construction-site image and submits an initial question.
3. Backend stores the image and creates or reuses a conversation.
4. Agent model receives the user request, conversation context, and available tools.
5. Agent model calls `analyze_image` when image analysis is needed.
6. Backend calls an OpenAI-compatible Responses API VLM model.
7. VLM returns forced structured JSON.
8. Backend saves messages, image metadata, analysis result, tool calls, and model responses.
9. Frontend shows the answer and structured hazard result.
10. User asks follow-up questions such as:
    - "判断依据是什么?"
    - "哪个隐患最严重?"
    - "应该怎么整改?"
11. Agent model uses saved conversation context and tool results to call the relevant tool and answer.

## Technology Choices

- Backend: FastAPI
- Frontend: React with Vite
- Database: SQLite
- VLM integration: OpenAI-compatible Responses API
- Agent model integration: OpenAI-compatible Responses API
- Agent orchestration: Responses API tool calling / function calling
- Authentication: none for v0.1, local single-user demo only

## Model Configuration

v0.1 uses separate model roles:

- `VLM_MODEL`: analyzes images and returns structured hazard JSON.
- `AGENT_MODEL`: selects tools, interprets follow-up questions, and writes final answers.

v0.1 may use a shared API base URL and API key:

- `OPENAI_API_BASE_URL`
- `OPENAI_API_KEY`
- `VLM_MODEL`
- `AGENT_MODEL`

Future versions may split VLM and Agent credentials if needed.

## Agent Tools

v0.1 includes exactly these tools:

### `analyze_image`

Analyzes one uploaded construction-site image through the VLM model.

Expected use:

- Initial image analysis.
- Re-analysis when the user uploads a new image in the same conversation.

### `explain_basis`

Explains why one or more hazards were identified.

Expected use:

- User asks about evidence, basis, or reasoning.
- User asks why something is considered unsafe.

### `rank_risks`

Ranks hazards by severity.

Expected use:

- User asks which hazard is most serious.
- User asks for priority order.

### `suggest_remediation`

Provides remediation suggestions for identified hazards.

Expected use:

- User asks how to fix, mitigate, or rectify hazards.
- User asks for action recommendations.

## VLM Structured Output

The VLM must return JSON matching this conceptual schema:

```json
{
  "summary": "string",
  "hazards": [
    {
      "name": "string",
      "location": "string",
      "risk_level": "low | medium | high | critical",
      "basis": "string",
      "remediation": "string",
      "confidence": 0.0
    }
  ],
  "needs_followup": false,
  "followup_question": null
}
```

Field intent:

- `summary`: overall safety assessment for the image.
- `hazards`: list of detected or suspected hazards.
- `name`: concise hazard name.
- `location`: visible position or region in the image.
- `risk_level`: one of `low`, `medium`, `high`, `critical`.
- `basis`: visual or contextual evidence used for the judgment.
- `remediation`: practical correction suggestion.
- `confidence`: number from `0.0` to `1.0`.
- `needs_followup`: whether the Agent needs more information from the user.
- `followup_question`: optional question when more information is needed.

## Persistence Requirements

v0.1 stores full local audit memory in SQLite.

Required records:

- `conversations`: conversation identity and timestamps.
- `messages`: user and assistant messages.
- `uploaded_images`: image path, MIME type, file size, and association to conversation.
- `analysis_results`: structured VLM hazard JSON.
- `tool_calls`: tool name, input, output, status, duration, and timestamps.
- `model_responses`: raw Agent and VLM responses, errors, and metadata.

This is acceptable for local MVP debugging. Later production-oriented versions must add retention, redaction, privacy controls, and sensitive data handling.

## Frontend Requirements

The v0.1 UI should be minimal but usable:

- Image upload control.
- Text input for initial question and follow-up questions.
- Conversation transcript.
- Structured hazard list display.
- Basic loading and error states.
- Show latest analysis result for the current conversation.

The UI should not attempt to become a full dashboard in v0.1.

## Backend API Requirements

v0.1 needs enough API surface for the UI:

- Upload an image or send image plus message.
- Send a follow-up message with `conversation_id`.
- Return:
  - `conversation_id`
  - assistant answer
  - latest structured analysis result when available
  - tool calls or debug metadata for local inspection

Exact endpoints are implementation details for the planning phase.

## Non-Goals

v0.1 does not include:

- Multi-image comparison.
- Report generation.
- Human review workflow.
- Remediation task management.
- Annotation feedback loop.
- Training data generation.
- Rule database or regulation citation engine.
- User login.
- Multi-user isolation.
- Permissions or audit policy suitable for production.
- Deployment automation.

## Acceptance Criteria

v0.1 is complete when:

1. A user can start the app locally.
2. A user can upload one construction-site image from the web UI.
3. The backend calls a real OpenAI-compatible Responses API VLM model.
4. The VLM result is parsed and stored as structured JSON.
5. The Agent model uses tool calling for at least the initial image analysis path.
6. The user can ask at least three follow-up types:
   - basis explanation
   - risk ranking
   - remediation suggestion
7. SQLite stores conversation, messages, uploaded image metadata, analysis result, tool calls, and model responses.
8. The frontend shows the assistant answer and structured hazards.
9. Local tests cover the core Agent tool flow and JSON parsing path.

## Open Questions For Planning

- Which exact Responses API model names will be used for `VLM_MODEL` and `AGENT_MODEL`?
- Should images be sent to the VLM as base64 data URLs or uploaded file references?
- Should raw image files be stored under a local `runtime/` directory?
- What should happen when VLM JSON parsing fails?
- Should model response storage include full raw content by default, or should it be controlled by a debug flag even in v0.1?
